# Architecture

Wrapsfer follows Clean Architecture with CQRS. Five projects under `src/`,
inward-pointing dependencies, no inversions. New behavior is added module
by module — Products and Waybills are the two reference modules.

## Project Layout

```text
src/
  Wrapsfer.Api/                ASP.NET Core host
    Controllers/V1/            ProductsController, WaybillsController, ...
    Contracts/                 Request DTOs that map onto MediatR commands
    Filters/TenantResolutionFilter.cs
    Extensions/                ServiceCollectionExtensions, WebApplicationExtensions
  Wrapsfer.Application/        MediatR-driven use cases
    Abstractions/              ITenantContext, ICommand/IQuery, file processing, queue
    Behaviors/                 ValidationBehavior, LoggingBehavior, RequestLoggingSanitizer
    Common/                    PagedResult<T>
    Products/, Waybills/, TenantSettings/, StockAlerts/
                               Commands/, Queries/, EventHandlers/, Messaging/, Responses/
  Wrapsfer.Domain/             Aggregates and domain primitives
    Abstractions/              IUnitOfWork, IDomainEventHandler, DomainEventNotification<T>
    Common/                    Result, Result<T>, Error, ErrorType, BaseEntity, AuditableEntity, AuditLog
    Entities/                  Product, ProductComponent, Waybill, WaybillItem, TenantSettings, ...
    Enums/                     ProductType, WaybillStatus, StockAlertType, StockAlertDeliveryStatus
    Errors/                    Per-aggregate static error catalogues
    Events/                    Domain events (LowStockDetected, WaybillPacked, ...)
    Repositories/              Repository interfaces
  Wrapsfer.Infrastructure/     Concrete adapters
    Authentication/            Keycloak realm resolution + JWT events
    BackgroundServices/        Hosted services (export consumers, stale-draft job)
    Configuration/             Infisical secrets provider + options
    FileProcessing/            CSV/XLSX parsers and writers
    Migrations/                EF Core migrations + ApplicationDbContextModelSnapshot
    Persistence/               ApplicationDbContext, Configurations, Interceptors, Repositories
    Queue/                     RabbitMqMessagePublisher + queue extensions
  Wrapsfer.Mailing/            Email subsystem (independent module)
    Abstractions/              IMailer, MailMessage, MailRequestId
    Queue/                     RabbitMqMailer (publisher) + MailProcessingConsumer
    Resend/                    FluentEmailMailSender + ResendOptions
    Templates/                 ITemplateRenderer (Fluid) + Templates/Files/{...}
tests/
  Wrapsfer.Application.Tests/  Handler/validator unit tests
  Wrapsfer.Domain.Tests/       Entity invariants
  Wrapsfer.Mailing.Tests/      Template + queue tests
  Wrapsfer.IntegrationTests/   WebApplicationFactory-based tests
```

## Dependency Direction

```text
Api ──► Application ──► Domain
 │           ▲             ▲
 ▼           │             │
Infrastructure ────────────┘
 ▲
 │
Mailing  (independent of Domain/Application)
```

- `Api` is the composition root and references `Application`, `Infrastructure`,
  and `Mailing`.
- `Infrastructure` depends on `Application` (abstractions like
  `ITenantContext`, `IUnitOfWork`) and `Domain`.
- `Application` depends only on `Domain`.
- `Mailing` is a standalone module — no `Domain`/`Application` references —
  so it can be reused by any caller.
- `Domain` has no project references.

## CQRS With MediatR

Every use case is a `MediatR.IRequest<TResponse>`:

- **Commands** implement `ICommand<TResponse>` (or `ICommand` for void
  outcomes) and return `Result<T>` / `Result`. Examples:
  `CreateProductCommand`, `MarkWaybillPackedCommand`.
- **Queries** implement `IQuery<TResponse>` and return
  `Result<TResponse>`. Examples: `GetProductByIdQuery`,
  `ListWaybillsQuery`.
- **Handlers** implement `ICommandHandler<TCommand, TResponse>` /
  `IQueryHandler<TQuery, TResponse>` and live next to the request type
  (`Application/Products/Commands/CreateProduct/CreateProductCommandHandler.cs`).

Controllers are thin: they construct the command from the HTTP body, send
it through `ISender`, and pipe the resulting `Result` through
`ApiControllerBase.ToActionResult` / `ToCreatedResult`.

### Pipeline Behaviors

`Wrapsfer.Application` registers two MediatR pipeline behaviors
(in `Application/DependencyInjection.cs`):

1. **`ValidationBehavior<TRequest, TResponse>`** — runs all registered
   FluentValidation validators for the request type before the handler.
   Aggregated failures return as `ErrorType.Validation` `Result`s.
2. **`LoggingBehavior<TRequest, TResponse>`** — structured request/response
   logs through Serilog. `RequestLoggingSanitizer` redacts properties
   marked `[SensitiveData]`.

## Result Pattern

Domain methods that can fail return `Result<T>` (`Wrapsfer.Domain.Common`).
`Error` is a value object: `Code`, `Description`, `Type` (`Validation`,
`NotFound`, `Conflict`, `Failure`). Errors are declared as `static readonly`
fields on per-aggregate error catalogues — e.g. `ProductErrors.NotFound`,
`WaybillErrors.CannotEditNonDraft`. **No inline `new Error(...)`.**

`ApiControllerBase` maps `Error.Type` to HTTP status codes; see
[Errors & Validation](../api/errors-validation).

## Domain Events

Aggregates raise events by appending to `BaseEntity.DomainEvents`. Examples:

- `LowStockDetectedEvent` / `StockRecoveredEvent` (Product).
- `WaybillCreatedEvent`, `WaybillPackedEvent`, `WaybillHandedOffEvent`,
  `WaybillCancelledEvent`, `WaybillItemAddedEvent` (Waybill).

`DomainEventInterceptor` (registered as a `SaveChangesInterceptor`)
collects every event from tracked entities after a successful
`SaveChangesAsync`, wraps each in `DomainEventNotification<T>`, and
publishes it through MediatR. Handlers (`IDomainEventHandler<TEvent>` →
`INotificationHandler<DomainEventNotification<TEvent>>`) live in
`Application/{Module}/EventHandlers/`. Events are cleared from the
entities after publication.

This makes side effects (alert emails, logs, downstream messaging) fire
**after** the database transaction commits.

## EF Core Persistence

`ApplicationDbContext` (in `Wrapsfer.Infrastructure.Persistence`) exposes
DbSets for `Product`, `ProductComponent`, `TenantSettings`,
`NotificationRecipient`, `StockAlertLog`, `Waybill`, `WaybillItem`, and
`AuditLog`. It also implements `IUnitOfWork` (the `Wrapsfer.Domain`
abstraction).

Per-entity configuration lives in
`Infrastructure/Persistence/Configurations/*Configuration.cs`. Tenant
isolation is enforced as a code rule — every repository method takes a
`tenantId` and filters by it; the `(tenantId, key)` indexes back this
up. Concurrency tokens use PostgreSQL's `xmin` system column where
needed (e.g. stock fields).

### Interceptors

Three `SaveChangesInterceptor`s are attached to the `DbContext`:

| Interceptor                  | Hook        | Purpose                                                                |
| ---------------------------- | ----------- | ---------------------------------------------------------------------- |
| `AuditableEntityInterceptor` | SavingChanges | Sets `CreatedAt/By` and `UpdatedAt/By` on every `AuditableEntity`.   |
| `AuditLogInterceptor`        | SavingChanges | Appends an `AuditLog` row per Add/Update/Delete (excluding `AuditLog` itself). Redacts `[SensitiveData]` properties. |
| `DomainEventInterceptor`     | SavedChangesAsync | Publishes domain events through MediatR after a successful save. |

`AuditableEntityInterceptor` and `AuditLogInterceptor` use `ITenantContext`
to capture the acting user/tenant; both swallow access errors so background
services without an HTTP scope still save successfully.

## Repository Pattern

Repository interfaces live in `Wrapsfer.Domain.Repositories`; concrete
implementations are in `Wrapsfer.Infrastructure.Persistence.Repositories`:

- `IProductRepository`, `IProductComponentRepository`,
  `ITenantSettingsRepository`, `IStockAlertLogRepository`,
  `IWaybillRepository`.

Every read/mutate method requires `tenantId`. Repositories project to
domain types — they do not expose `IQueryable` upward. Batch operations
(`GetByIdsAsync`, `GetByBarcodesAsync`) exist to avoid N+1 fetches in
imports and the stock reservation service.

## Adding A Module

The Products module is the canonical reference. To add a new module:

1. **Domain** — entity (aggregate root) in `Domain/Entities/`, error
   catalogue in `Domain/Errors/`, repository interface in
   `Domain/Repositories/`, domain events in `Domain/Events/`.
2. **Application** — `Commands/` and `Queries/` folders with
   `Command/Query`, `Handler`, and `Validator` per use case. Response
   DTOs in `{Module}/Responses/`. Domain event handlers in
   `{Module}/EventHandlers/`.
3. **Infrastructure** — repository implementation and EF configuration in
   `Persistence/`. Register the repository in
   `Infrastructure.DependencyInjection.AddInfrastructure`.
4. **Api** — controller in `Controllers/V1/`. Apply
   `[ServiceFilter(typeof(TenantResolutionFilter))]` if owner-realm
   override should apply. Inherit `ApiControllerBase` for `[Authorize]`
   + result mapping. Request DTOs in `Contracts/`.
5. Add tests across `Wrapsfer.Domain.Tests`,
   `Wrapsfer.Application.Tests`, and `Wrapsfer.IntegrationTests`.
