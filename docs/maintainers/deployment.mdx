# Deployment

What ships with the Wrapsfer API for running it as a container, and what
to think about before deploying outside local development. The repo
includes a multi-stage `Dockerfile` and a `compose.yaml` that stands up
the full stack (API + Postgres + RabbitMQ + Keycloak). There is no
infrastructure-as-code or CI/CD pipeline checked in.

For local non-Docker runs, see
[Getting Started](../api/getting-started). For the configuration the
runtime reads, see [Configuration](./configuration).

## Image

The `Dockerfile` is a standard ASP.NET Core 10 multi-stage build:

- Build stage: `mcr.microsoft.com/dotnet/sdk:10.0` — restores the
  solution, then publishes `src/Wrapsfer.Api/Wrapsfer.Api.csproj`
  (`-c Release`).
- Runtime stage: `mcr.microsoft.com/dotnet/aspnet:10.0`, runs as the
  non-root `app` user.
- Default environment variables baked into the runtime image:

  ```
  ASPNETCORE_URLS=http://+:8080
  ASPNETCORE_ENVIRONMENT=Production
  DOTNET_NOLOGO=true
  DOTNET_CLI_TELEMETRY_OPTOUT=true
  ```

- `EXPOSE 8080`. Entry point: `dotnet Wrapsfer.Api.dll`.

Build the image:

```bash
docker build -t wrapsfer-api:local .
```

Run it directly (you must supply config — the API will not start
without `ConnectionStrings__DefaultConnection`, RabbitMQ keys, etc.):

```bash
docker run --rm -p 8080:8080 \
  -e ConnectionStrings__DefaultConnection="Host=...;Database=wrapsfer;..." \
  -e RabbitMq__HostName=rabbit-host \
  -e RabbitMq__UserName=... -e RabbitMq__Password=... \
  -e Keycloak__BaseUrl=https://auth.example.com \
  -e Keycloak__Audience=wrapsfer-api \
  -e Mailing__Resend__ApiKey=... \
  -e Mailing__Resend__FromAddress=noreply@example.com \
  wrapsfer-api:local
```

## `compose.yaml` (Full Stack)

The repo also ships `compose.yaml` for spinning up the API alongside
Postgres, RabbitMQ, and Keycloak — useful for full-stack local runs and
as a reference for production wiring. Required environment variables
(set in a `.env` next to the file or in your shell):

| Variable                    | Purpose                                                |
| --------------------------- | ------------------------------------------------------ |
| `DOCKER_IMAGE`              | API image name (without tag). Used as `${DOCKER_IMAGE}:${IMAGE_TAG:-latest}`. |
| `IMAGE_TAG`                 | Optional. Defaults to `latest`.                        |
| `API_PORT`                  | Optional. Defaults to `8080`.                          |
| `ASPNETCORE_ENVIRONMENT`    | Optional. Defaults to `Production`.                    |
| `DB_USER`, `DB_PASSWORD`, `DB_NAME` | Postgres credentials.                          |
| `DB_CONNECTION_STRING`      | Full connection string the API consumes (typically `Host=db;…;Database=${DB_NAME};Username=${DB_USER};Password=${DB_PASSWORD}`). |
| `RABBITMQ_USER`, `RABBITMQ_PASSWORD`, `RABBITMQ_HOST` | RabbitMQ credentials and host (`rabbitmq`). |
| `RESEND_API_KEY`, `RESEND_FROM_ADDRESS`, `RESEND_FROM_NAME` | Resend mailing config. |
| `KEYCLOAK_*`                | Realm, audience, admin credentials, DB password, port. |

Bring it up:

```bash
docker compose up -d --build
docker compose logs -f api
docker compose down
```

The Postgres and RabbitMQ services declare healthchecks; the API
service waits on them via `depends_on.condition: service_healthy`.

## Production Considerations

The default `Dockerfile` runtime environment is **`Production`** — the
opposite of the local launch profiles. In `Production`:

- **OpenAPI is not exposed.** `/openapi/v1.json` is only mapped when
  `app.Environment.IsDevelopment()`. Don't change that without first
  deciding how to protect the document — see
  [OpenAPI → Production Exposure](../api/openapi#production-exposure).
- **Detailed exception details are still hidden.** The exception
  handler returns generic `ProblemDetails` regardless of environment;
  raw stack traces never reach the wire. See
  [Errors & Validation](../api/errors-validation).

Other items to plan deliberately before any non-local deployment:

### Authentication

Wrapsfer requires a working Keycloak with the realms your tenants need.
Configure:

- `Keycloak:BaseUrl` — must be reachable from the API container.
- `Keycloak:OwnerRealm` — the staff/admin realm (default `owner`).
- `Keycloak:Audience` — must match the JWT `aud` claim issued for
  this API (default `wrapsfer-api`).
- `Keycloak:RequireHttpsMetadata = true` for production (the runtime
  default). Only set to `false` for local Keycloak over HTTP.

See [Authentication & Tenancy](../api/authentication-tenancy) and
[Authentication Internals](./authentication-internals).

### TLS

The container exposes HTTP on `8080`. `app.UseHttpsRedirection()` is in
the pipeline, but production deployments should terminate TLS upstream
(load balancer, ingress, reverse proxy) and forward HTTP to the
container. If TLS termination happens at the container, supply HTTPS
bindings via `ASPNETCORE_URLS` and the appropriate certificate
configuration.

### Database

- Provision PostgreSQL separately (managed service or a dedicated host).
- Apply pending migrations before promoting an image:

  ```bash
  export WRAPSFER_DESIGN_CONNECTION="<production connection string>"
  dotnet ef database update \
    --project src/Wrapsfer.Infrastructure/Wrapsfer.Infrastructure.csproj \
    --startup-project src/Wrapsfer.Api/Wrapsfer.Api.csproj
  ```

  In a CI flow, run the equivalent `dotnet ef migrations script`
  output through your migration tooling — see
  [Database & Migrations](./database-migrations).

### Secrets

Do not bake secrets into images. Inject them through environment
variables (Compose `.env`, Kubernetes Secrets, ECS task definitions,
etc.). For longer-term storage, the optional Infisical integration
loads secrets from your Infisical project on startup — see
[Configuration → Infisical](./configuration#infisical).

### Observability

The repo ships:

- **Serilog** with the console sink and `FromLogContext`,
  `WithMachineName`, `WithThreadId` enrichers.
- **Health checks** at `/health`, aggregating Npgsql and RabbitMQ.

Add additional sinks (Seq, Elasticsearch, OTLP) by referencing the
package and listing it under the `Serilog:Using` and `Serilog:WriteTo`
sections of `appsettings.{Environment}.json` or environment overrides.

There is no metrics or distributed-tracing framework wired in today —
add OpenTelemetry separately if needed.

### CORS And Allowed Hosts

Both default to permissive values:

- `AllowedHosts: "*"` in `appsettings.json`.
- No `Cors` policy is registered in source — controllers run without
  cross-origin restrictions.

Tighten both before a public deployment: set `AllowedHosts` to the
hostnames you actually serve and add a CORS policy if browser clients
will call the API.

### Background Services

The API process hosts three background services:

- `ProductsExportConsumer`
- `WaybillsExportConsumer`
- `AutoCancelStaleDraftsJob` (hourly)

Running multiple instances of the API container is safe — RabbitMQ
distributes export messages across consumers, and the stale-draft job
takes per-waybill scopes (race losers will simply find the waybill
already cancelled and skip). See
[Messaging & Background Jobs](./messaging-background-jobs) for details.

### Deployment Platform

The `Dockerfile` and `compose.yaml` make no assumptions about a
specific cloud or orchestrator. The image is a standard ASP.NET Core 10
container and can run anywhere a container can run — Kubernetes, ECS,
Cloud Run, Azure Container Apps, plain Docker on a VM. Pick a target
deliberately and supply platform-specific manifests separately;
nothing in this repo is tailored to one.
