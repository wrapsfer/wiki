# Testing

The Wrapsfer API has four test projects under `tests/`. Together they cover
domain invariants, application handlers/validators, the mailing module,
and end-to-end HTTP behavior.

| Project                       | References                              | Scope                                                            |
| ----------------------------- | --------------------------------------- | ---------------------------------------------------------------- |
| `Wrapsfer.Domain.Tests`       | `Wrapsfer.Domain`                       | Pure domain rules — entity factories, mutators, `Result` failures. |
| `Wrapsfer.Application.Tests`  | `Wrapsfer.Application`, `Wrapsfer.Domain` | Handler and validator behavior. Repositories are mocked via Moq. |
| `Wrapsfer.Mailing.Tests`      | `Wrapsfer.Mailing`                      | Template rendering, queue envelope serialization, retry policy. |
| `Wrapsfer.IntegrationTests`   | `Wrapsfer.Api`                          | `WebApplicationFactory<Program>`-based HTTP tests.               |

The frameworks are **xUnit + Moq + FluentAssertions**, with
`coverlet.collector` for coverage. Solution file is `Wrapsfer.slnx`.

## Running Tests

```bash
make restore          # dotnet restore
make build            # dotnet build --no-restore
make test             # dotnet test --no-restore --no-build
```

Subset commands:

```bash
# Single project
dotnet test tests/Wrapsfer.Domain.Tests
dotnet test tests/Wrapsfer.Application.Tests
dotnet test tests/Wrapsfer.Mailing.Tests
dotnet test tests/Wrapsfer.IntegrationTests

# Single test by FQN substring
dotnet test --no-restore --no-build \
  --filter "FullyQualifiedName~CreateProductCommandHandlerTests.Handle_ReturnsConflict_WhenBarcodeExists"

# Coverage
dotnet test --collect:"XPlat Code Coverage"
```

The integration tests host the API in-process; no separate `dotnet run`
is needed. They share infrastructure connections via the standard
`IClassFixture<WebApplicationFactory<Program>>` pattern.

## What Each Project Covers

### `Wrapsfer.Domain.Tests`

Tests pin the invariants in `Wrapsfer.Domain.Entities` aggregates and
their `*Errors` static catalogues:

- `Product` — factory validation, stock mutations, threshold-event
  emission, unpack mechanics.
- `Waybill` — status transitions, item add/update/remove rules,
  cancellation invariants, hand-off creator-only check.
- `TenantSettings` — recipient add/remove, email format check.

Domain tests have **zero framework dependencies** beyond xUnit; do not
introduce HTTP, EF, or DI types here.

### `Wrapsfer.Application.Tests`

Tests handlers and validators for each module's `Commands/` and
`Queries/`. Pattern:

- Mock `IProductRepository`, `IWaybillRepository`,
  `IUnitOfWork`, `ITenantContext`, `IMessagePublisher`, `IMailer` via
  Moq.
- Use FluentAssertions for `Result<T>` and `Result` checks
  (`result.IsSuccess.Should().BeTrue()`, etc.).
- Run handlers directly without MediatR; behaviors
  (`ValidationBehavior`) are tested separately.

### `Wrapsfer.Mailing.Tests`

Tests for the standalone mailing module:

- `FluidTemplateRenderer` — renders the on-disk Liquid templates with a
  given token dictionary.
- `RabbitMqMailer` — envelope serialization (`MailRequestedMessage`),
  required-field validation (`To`, mutually-exclusive
  `Subject/Body` vs. `TemplateName`).
- `MailRetryPolicy` — backoff schedule for transient failures.

### `Wrapsfer.IntegrationTests`

Boots the real ASP.NET Core host with `WebApplicationFactory<Program>`.
`Program.cs` declares `public partial class Program;` so the entry
point is addressable. Each test class uses
`IClassFixture<WebApplicationFactory<Program>>` to share the host
across the class.

These tests are scaffolded today — extend them when adding new
endpoints. Common substitutions:

- Override `JwtBearer` validation with a test scheme that accepts a
  fake token.
- Replace `IMessagePublisher` and `IMailer` with in-memory test doubles
  to avoid hitting RabbitMQ in CI.
- Replace `ApplicationDbContext` with a Postgres test database (or
  Testcontainers) when full DB behavior is required.

## Conventions From `CLAUDE.md`

These project-wide rules influence how tests are written:

- **No `var`.** Always use explicit types (enforced by
  `dotnet format style` and a pre-commit hook).
- **One type per file.** Every test class, helper, or fake gets its own
  file.
- **Tenant isolation.** Repository tests must always exercise the
  `tenantId` argument; never simulate "global" reads.
- **Domain validation via `Result`.** Assert on `Result.IsSuccess` /
  `Result.Error.Code`, not on thrown exceptions, for business
  validation paths.
- **Concurrency.** When a test exercises stock mutation paths, pin the
  expected `xmin`-style concurrency token behavior (e.g. throwing
  `DbUpdateConcurrencyException` on stale updates).

## Quality Check Commands

Run before committing:

```bash
make restore
make build           # TreatWarningsAsErrors is on globally — warnings will fail.
make test
make format-all      # whitespace + style fixes (dotnet format + dotnet format style)
```

`format-all` runs `dotnet format` followed by `dotnet format style`. The
pre-commit hook enforces `var`-free code and the no-consecutive-blank-lines
rule.
